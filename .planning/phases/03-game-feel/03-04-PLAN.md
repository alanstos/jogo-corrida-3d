<objective>
Implement camera shake on collision (FEEL-03): the chase camera receives a small, exponentially-decaying random offset on its lerp target for ~300ms after a collision, producing the arcade-game "hit reaction" without touching physics or the car mesh. The shake is purely cosmetic — it modifies what the camera looks at, not where the car is.

Purpose: Camera shake is the cinematic counterpart to the collision particles (Plan 03-03). Together they form the "impact moment" of the game feel triad (particles + shake + haptic). Of the three, shake is the most subtle but the most critical for conveying weight — without it, even with particles, collisions feel weightless.

Output: Camera.js extended with shake state, decay logic, and a startShake() method; Game.js wired to call startShake() at the same collision-handler site that bursts particles. Strict invariant: physics is never touched by shake code.
</objective>

  <action>
    Three additions to Camera.js:

    A. Module-level constants — declare after `import * as THREE from 'three';` (L1), BEFORE `export default class Camera` (L3):
    - `const SHAKE_DURATION = 0.3;` — nominal shake duration in seconds; the actual end is driven by amplitude decay, this constant is informational and tunable
    - `const SHAKE_DECAY = 15;` — exponential decay rate constant; higher = faster fade. At DECAY=15, after 0.2s the amplitude is ~5% of original; after 0.3s it's ~1%
    - `const SHAKE_INTENSITY = 0.35;` — peak shake amplitude in world units. With the chase cam at offset (0, 3, 8) from a car that's ~4 units long, 0.35 is a visible but non-nauseating shake. Tunable per RESEARCH Assumption A3.

    B. Constructor (L16-25) — add three new fields after the existing `this._offset = new THREE.Vector3(0, 3, 8);` (L21) and BEFORE the existing `this.instance.position.set(0, 3, 8);` (L24):
    - `this._shakeAmplitude = 0;` — current shake amplitude; 0 means no active shake
    - `this._shakeElapsed = 0;` — seconds since the current shake started; used in the decay formula
    - `this._shakeVec = new THREE.Vector3();` — PRE-ALLOCATED scratch vector reused every frame during shake. Pitfall #3 explicitly forbids `new THREE.Vector3()` inside follow().

    C. follow(carMesh, deltaTime) (L34-46) — extend the existing method. The existing body:
    - Line 37: `const targetPos = carMesh.localToWorld(this._offset.clone());`
    - Lines 39-42: alpha + lerp
    - Line 45: lookAt

    Insert the shake block BETWEEN line 37 (targetPos computation) and line 41 (alpha computation):

    1. Guard: if `this._shakeAmplitude > 0.001`, the shake is active.
    2. Increment `this._shakeElapsed += deltaTime`.
    3. Compute current amplitude: `const amp = this._shakeAmplitude * Math.exp(-SHAKE_DECAY * this._shakeElapsed);`.
    4. If `amp < 0.001`, the shake is effectively done: set `this._shakeAmplitude = 0` and skip the offset write this frame. (Do not set `_shakeElapsed = 0` here — startShake() resets it.)
    5. Otherwise: regenerate `this._shakeVec` in-place via `this._shakeVec.randomDirection().multiplyScalar(amp);`. randomDirection() mutates the vector to a random unit vector — no new allocation. Then add it to targetPos: `targetPos.add(this._shakeVec);`. (THREE.Vector3.add mutates the left operand in place; targetPos was created by localToWorld which returns the mutated input — the .clone() at line 37 ensures we are mutating a fresh copy each frame, NOT the original _offset.)

    The lerp at line 42 (`this.instance.position.lerp(targetPos, alpha);`) and the lookAt at line 45 are unchanged — they operate on the (potentially shake-offset) targetPos transparently. CRITICAL: lookAt receives `carMesh.position` (not targetPos), so the camera always aims at the car center even while its position jitters. This is what produces the "shake" feel rather than a "drift" feel.

    D. Add a new public method `startShake()` to the class (place after follow(), before onResize(), to keep methods grouped by category):
    - Set `this._shakeAmplitude = SHAKE_INTENSITY`
    - Set `this._shakeElapsed = 0`

    The method takes no arguments — the constants drive the behavior. If future tuning needs per-call intensity (e.g. a "big hit" shake), the method can be extended with an optional parameter; for now it is parameterless.

    Do not modify the existing `_offset`, the lerp `alpha = 1 - Math.exp(-10 * deltaTime)` formula, the `lookAt(carMesh.position)` call, or `onResize`. The shake is purely additive — when `_shakeAmplitude === 0`, follow() behaves byte-identically to the current v1.0 implementation.

    Hard constraint: inside the body of `follow()`, there must be ZERO `new THREE.Vector3` calls. The only `new THREE.*` calls in Camera.js are in the constructor (PerspectiveCamera, Vector3 for _offset, Vector3 for _shakeVec). Confirm via the awk gate in the verify command.
  </action>

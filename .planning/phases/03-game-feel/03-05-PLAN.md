<objective>
Implement haptic feedback (FEEL-04): on devices that support the Vibration API, the controller vibrates briefly when the player activates turbo (~50ms) and when the car collides with an obstacle (~100ms). On devices without the API (iOS, Firefox 129+), the calls are silently no-ops — no console errors, no thrown exceptions, no degraded gameplay. This is the third leg of the multi-modal feedback triad: particles (visual) + camera shake (kinetic) + haptic (tactile).

Purpose: Plan 03-05 is intentionally last in the phase because it depends on the event sites that Plans 03-02 (turbo state machine) and 03-03 (collision handler) created. Wiring haptic here is a single-line edit at each site; the abstraction lives in a tiny new module (game/Haptic.js) that owns the cross-browser guard.

Output: New module game/Haptic.js exporting a `vibrate(pattern)` function with the precise `typeof === 'function'` guard; Game.js imports it and calls it at the two event sites established by Waves 1-2.
</objective>

  <action>
    Create a new file `game/Haptic.js`. The module follows the existing project conventions: ES module with named export(s), no default export (this is a single utility function, not a class — distinct from Car/Track/Camera/HUD which are classes).

    File contents — exactly one named export `vibrate`:

    Define an exported function `vibrate(pattern)`. The parameter `pattern` accepts either:
    - A single number (e.g. `50`) — vibrates for that many milliseconds
    - An array of numbers (e.g. `[50]` or `[100, 30, 100]`) — sequence of vibration/pause durations

    Both forms are valid `navigator.vibrate` arguments per the W3C Vibration API. The planning brief specifies `vibrate([50])` and `vibrate([100])` (array form) — accept arrays as the canonical call form. Single-number form is also accepted because the underlying API accepts both, and rejecting it would force callers to wrap.

    Function body:
    1. Guard: `if (typeof navigator === 'undefined') return;` — defensive guard for any non-browser context (unit tests in node, server-side rendering). Cheap and not in the hot path.
    2. Guard: `if (typeof navigator.vibrate !== 'function') return;` — THIS IS THE CRITICAL CHECK. Pattern: `typeof ... === 'function'`. Do NOT use `if (navigator.vibrate)` — that would incorrectly pass on browsers where `navigator.vibrate` is defined but returns a falsy value, and would still throw on browsers where the property is genuinely undefined. The function check is precise.
    3. Call: `navigator.vibrate(pattern);` — the call itself never throws on valid args; it returns `true` on success and `false` if the pattern is invalid (per W3C spec). Either return value is fine — the caller does not consume it.

    No other exports, no class, no default export. The entire module is ~10 lines including the function signature and the two guard returns.

    Documentation comment above the export — a short JSDoc explaining the cross-browser guard rationale (iOS never supported, Firefox 129+ removed) so future maintainers do not "simplify" the typeof check into a truthy check.

    Hard constraint: the module must NOT import THREE, cannon-es, or any other game module. It is a leaf utility with zero dependencies. The only global it touches is `navigator`.
  </action>
